AI Coding 工作流

1. 用规范文档来帮助开发

流程

  • Explore：理解目标、现有代码和约束。
  • Specification（Spec，规格说明）：定义“做什么、为什么做、验收标准”，并挑战其中的假设。
  • Plan：定义“怎么实现”，审查方案后在同一文件中拆成小任务。
  • Execute：一次实现一个任务，并逐任务验证。
  • Converge：执行完整检查并独立审查，确保 Spec、Plan、代码和结果记录一致。

AI 擅长搜索、归纳、生成和执行，但不会知道隐含需求，也不应替开发者做未声明的产品与架构决策。好的流程不是让 AI 一次写出更多代码，而是让错误更早、以更低成本暴露。

2. 流程介绍

阶段 主要目的 输入 输出
1. Explore 摸清现状与改动边界 用户目标、issue、仓库、日志、设计稿 上下文地图、相关文件与测试、约束与未知项
2. Specification（Spec） 把意图写成行为契约 目标与探索结果 spec.md：行为契约与验收标准
3. Plan 定方案、拆任务 已确认的 Spec、项目约束 plan.md：方案与任务清单
4. Execute 小步实现与验证 单个已批准任务、相关代码 代码与测试 diff、逐任务验证证据
5. Converge 完整验证与独立复核 Spec、Plan、最终 diff、测试结果 result.md：收敛结论

2.1 Explore：先理解，再建议

编辑前先阅读仓库说明并检查已有改动，再追踪当前行为，找到相关文件、依赖、相似实现、测试和验证命令。记录安全、兼容性等约束；仓库无法回答时，再查阅匹配当前版本的官方资料。

产出简明的“上下文地图”：现状、边界、相关文件、怎么验、未知。此阶段不写业务代码。

Prompt模版：

2.2 Specification（Spec）：定义行为，并挑战假设

Spec 关注 what / why，是需求和验收的 source of truth。写清背景（目标与用户）、要什么（场景与功能需求）、验收标准（含边界与约束）、不做什么（非目标与未决问题），不要过早规定技术实现。

初稿完成后，让 AI 以 critic 身份逐条挑刺：没说的（隐含假设）、说不清的（模糊要求与遗漏风险）、做多了的（过度设计与约束冲突）。澄清结论必须回写 spec.md，不能只留在聊天中。

Prompt模版：

2.3 Plan：设计、审查并拆解

Plan 关注 how：写清改什么（文件范围与接口）、怎么改（实现路径、数据流与关键取舍）、怎么验（测试策略与风险）。优先复用现有模式，选择最小可运行方案；只在明确需求或证据支持时增加复杂度。

编码前检查方案是否覆盖验收标准，是否存在更简单的做法，以及是否引入无关重构、新依赖、接口变化或未处理的安全与兼容性风险。

审查通过后，直接在 plan.md 中加入有序任务清单。每项任务都写清三件事：做什么、验收标准、怎么验；并且能独立实现和测试。

Prompt模版：

2.4 Execute：小步实现与验证

一次只实现 plan.md 中的一个已批准任务：

保持 diff 小，并为每个任务运行 targeted tests。只记录实际执行的检查；无法验证的项目要说明原因和风险。如果实现需要改变需求或架构，先更新 Spec 或 Plan，再继续编码。

Prompt模版：

2.5 Converge：完整验证与独立复核

全部任务完成后，运行单元测试和全量测试，性能验证。

让未参与实现的新会话对照 Spec、Plan、完整 diff 和测试结果，逐项复核漏做（需求遗漏与测试缺口）、偏离（与批准方案不一致）、夹带（非请求功能）、破坏（回归与安全问题）、过度设计（多余抽象与新增层）。发现缺口就在 plan.md 中追加任务，修复后再次 Converge。

最终把结果写入 result.md，回答四件事：做了什么、验了什么、没验什么、剩什么风险。只有影响后续维护的重要修复决策才写入 decisions.md。

Prompt模版：

3. 持久化

应保存在仓库中的 Markdown：

decisions.md 只记录会影响后续维护的重要选择，不必收纳每次普通测试失败。常规问题、修复和复测结果放入 result.md。每次需求或方案变化都更新对应工件，并检查下游内容是否需要同步。工件应简短、当前、可追踪；文档数量不是目标，可恢复的共同理解才是目标。
