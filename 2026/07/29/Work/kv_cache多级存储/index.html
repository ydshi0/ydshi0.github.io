KVCache多级存储
eric
  2026-07-29   2026-07-29
  • Work
  • KVCache

SGLang HiCache 把 GPU、Host 和外部存储组织成三级 Prefix Cache，核心是让 prefix 匹配、异步预取、跨层搬运、TP 一致性和回写策略共同工作，在不阻塞推理的前提下降低 TTFT 与 Prefill GPU 成本。

1. 为什么需要多级 Prefix Cache？

1.1 明确边界

两类问题：

  • 请求内活跃 KV：当前 Decode 请求的历史 KV，每生成一个 token 都要访问，直接放到慢层容易拖慢 TPOT。
  • 请求间 Prefix KV：已经计算完成、未来请求可能再次命中的公共前缀，例如 system prompt、多轮会话历史、RAG 模板和 Coding Agent 的仓库上下文。

HiCache 主要解决第二类问题。Prefix KV 只读、可重算、复用具有明显冷热分布，适合做分层缓存；miss 或 I/O 失败时也可以退化为 Prefill，而不影响正确性。

1.2 KV 容量

标准 K/V 表示下，单请求全模型 KV Cache 大小近似为：

[
S_{KV} = 2 \times L \times T \times H_{kv} \times D_h \times B
]

其中 (L) 是层数，(T) 是 token 数，(H_{kv}) 是 KV head 数，(D_h) 是 head dimension，(B) 是元素字节数。以 BF16、head dimension 128 为例：

模型形态 层数 KV heads 每 token KV 32K tokens
典型 8B GQA 32 8 128 KiB 4 GiB
典型 70B GQA 80 8 320 KiB 10 GiB

KV 容量随上下文长度和并发线性增长。PagedAttention 改善了 GPU 内分页分配、碎片与共享，但没有消除 HBM 容量上限

1.3 三级缓存

层级 典型介质 作用域 主要职责
L1 GPU HBM 实例私有 attention 可直接消费的热 KV
L2 Host DRAM 主机/实例私有 温 KV、L3 staging tier、异步 DMA 缓冲区
L3 NVMe、远端内存、分布式存储 节点或集群共享 长尾 Prefix KV、跨实例复用与冷启动恢复

L2 不是多余的一跳：

  • 温 KV 缓存：这些 prefix 当前没有被 attention 使用，因此不值得继续占用稀缺的 HBM；但它们刚被访问过或较可能再次命中，放在本机 DRAM 又比每次从远端 L3 读取更快、更稳定。
  • L3 staging tier（中转层）：L3 backend 返回的数据先写入预先分配的 L2 page，完整到达后标记为 ready，再从 L2 加载到 GPU。这样 GPU 不需要理解 Mooncake、3FS、NIXL 等后端协议，L3 的延迟抖动也不会直接改变 GPU KV allocator 的状态。
  • 异步 DMA 缓冲区：L2 通常使用 Host memory，物理页不会在传输期间被操作系统换出，GPU 可以通过 cudaMemcpyAsync 或 I/O kernel 异步访问。Cache controller 会保持源 page 和目标 GPU slots 的生命周期，直到 CUDA event 表示传输完成，从而允许搬运与其他 GPU 计算重叠。

所以 L2 既是可独立命中的缓存层，也是 L3→GPU 数据路径上的落地点和速度缓冲层。

2. SGLang HiCache

HiCache 将 SGLang 的 RadixAttention 扩展为 L1/L2/L3 三级 Prefix Cache。L1/L2 通常由单个推理实例管理，L3 可以被集群中的多个实例共享。在三个数据池之上，HiRadixTree 负责回答“prefix 在哪里”，Cache controller 负责跨层搬运，Scheduler 负责决定“这次请求复用多少、等多久以及何时进入 GPU”。

HiRadixTree 精确维护本地 L1/L2 元数据，但不在每个实例复制和持续同步整个 L3 索引。只有本地 miss 时才查询 L3。这一设计用按需远端查询，换取更低的本地元数据量和跨实例同步成本。

2.1 HiRadixTree

RadixAttention 用 RadixTree 匹配请求的最长公共 token prefix，并让共享 prefix 复用同一份 KV。

HiRadixTree 在相同 prefix 结构上增加本地分层元数据：节点的 value 指向 L1 GPU slots，host_value 指向 L2 Host slots，hash_value 保存各 page 的逻辑 key。节点不会保存远端节点、文件 offset 或 RDMA 地址，实际位置和存在性由 storage backend 解析。

L3 中的 Prefix KV 通常不是另一棵 RadixTree，而是以 page 为粒度的 key-value/object 集合。第 i 个 page 使用 position-aware 的链式 key：h_i = SHA256(h_{i-1} || tokens(page_i))。因此相同 token page 出现在不同 prefix 上下文时会得到不同 key，prefix 的顺序依赖被编码进 hash chain，而不需要在 L3 再维护树结构。

请求先在 HiRadixTree 中完成 L1/L2 Local Match；对本地 miss 的 suffix，Cache controller 从最后一个已知 page hash 开始逐页生成后续 keys，并用 batch_exists 找到 L3 中最长连续命中，再用 batch_get 将这些 pages 读入预分配的 L2 slots。完整 page 到达后，HiRadixTree 才加入对应的 host_value 和 hash_value。因此 L3 的“prefix”语义来自链式 page keys + 从头连续命中，而不是一棵远端 RadixTree。

2.2 一次请求的完整控制流

sequenceDiagram
    participant S as Scheduler
    participant T as HiRadixTree
    participant L3 as L3 Storage
    participant L2 as Host L2
    participant L1 as GPU L1

    S->>T: local_match(prompt tokens)
    T-->>S: L1 prefix + L2 suffix + local miss
    S->>L3: 查询 local miss 后的连续 pages
    L3-->>S: l3_hit_tokens
    S->>S: TP all_reduce(min) + threshold 判断
    S->>L3: 异步 prefetch
    L3-->>L2: page data
    L2-->>T: page ready，更新本地层级元数据
    S->>S: 按策略停止等待，再次 all_reduce(min)
    S->>L1: 为最终命中前缀分配 GPU slots
    L2-->>L1: layer-wise load
    S->>L1: Prefill 未命中的 suffix
    L1-->>L2: 按策略回写新 KV
    L2-->>L3: 只发布 L3 尚不存在的 pages

从请求视角看，HiCache 的关键路径可以压缩成六步：

  1. 在 HiRadixTree 中做 L1/L2 Local Match；

  2. 对本地 miss 的连续后缀查询 L3；

  3. 若 L3 的连续命中长度达到 prefetch_threshold（默认 256 tokens），则异步预取 L3→L2，并按策略决定等多久；这里比较的是“可连续复用的 token 数”，不是缓存命中率或队列长度；

  4. TP ranks 对最终可复用长度达成一致；

  5. 为 prefix 分配 L1 slots，把 L2 KV 复制到这些 GPU slots；这一步也称 promotion/load，即把同一份 KV 从较慢层加载到可被 attention 直接读取的更快层，并不表示修改优先级；

  6. 将新生成的 KV 按策略回写到 L2/L3。

2.3 Local Match：先确定本地最长连续前缀

Scheduler 用 prompt tokens 遍历 HiRadixTree，得到的不是简单 hit/miss，而是分层结果：

当 page_size > 1 时，匹配、传输和存储都以 page 为粒度。若匹配终点落在 RadixTree 节点内部，节点会在边界处分裂，后续请求便可复用精确的公共前缀。

命中情况 数据动作 计算动作
L1 full hit 无搬运 跳过整个命中前缀的 Prefill
L1 + L2 hit L2→L1 只计算本地未命中的 suffix
L3 hit L3→L2→L1 按实际到达长度计算剩余 suffix
Partial hit 只使用连续且 ready 的 pages 其余部分重新 Prefill
Full miss 不加载缓存 完整 Prefill，再按策略回写

2.4 L3 查询与预取

这里的 Prefetch 特指 L3→L2。Local Match 后，HiCache 查询 [l2_end, T)，只取与本地命中衔接的最长连续 L3 prefix；中间一旦缺 page，后面的命中也不能使用。只有该连续命中达到 prefetch_threshold（默认 256 tokens）才发起异步预取，避免为短 prefix 支付不划算的 I/O 固定成本。

预取会尽早启动，利用请求排队和 Scheduler 组 batch 的时间把 KV 搬入 L2。

best_effort：请求可以进入 Prefill batch 时立即终止预取；

timeout：等待预取完成或达到动态超时预算；

wait_complete：一直等到计划预取的数据全部完成。

2.5 TP 一致性

TP 场景中，每个 rank 持有自己的 KV shard。某个 page 只有在所有 ranks 都可用时，才能被整个请求复用。HiCache 在两个位置收敛可复用长度：

  1. L3 查询之后：对 l3_hit_tokens 做 all_reduce(op=min)，所有 ranks 使用一致的预取计划；
  2. Prefetch 结束之后：对实际 ready tokens 再取最小值，所有 ranks 使用相同的最终 prefix 长度。

第一次避免可用cache长度不一致，第二次避免传输差异。

2.6 L2→L1：逐层搬运如何与 Prefill 重叠？

无论 KV 原本就在 L2，还是刚从 L3 预取到 L2，attention 最终都需要它进入 GPU L1：

  1. Scheduler 为最终命中的 prefix 预留 GPU KV slots；
  2. Cache controller 根据 L2 page 地址和目标 GPU block 生成传输任务；
  3. 通过 cudaMemcpyAsync 或 GPU-assisted I/O kernel 把 Host KV 搬到 L1；
  4. 传输完成后，对应 GPU blocks 才能作为 attention 的历史 KV。

2.7 数据布局：同时服务逐层计算与大块 I/O

GPU attention 按 layer 消费 KV，L3 backend 则希望按完整 page 做大块 I/O。HiCache 因此让 L1 保持计算友好的 layer_first，L2 通过 --hicache-mem-layout 在两条路径之间取舍。

固定观察 K 或 V、并省略 head 等内部维度后，三种布局可简化为：

  • layer_first：同一 layer 的 tokens 连续，L2→GPU 最自然；但一个 page 被拆散到各个 layer 区域，不利于 L2↔L3 的 page 级大事务。
  • page_first：整个 page 连续，适合 L3 零拷贝；但 page 内按 token 交错 layers，加载某一 layer 时需要 kernel backend 做 strided gather。
  • page_first_direct：整个 page 连续，且每个 (page, layer) 也是连续块，既保留 L3 的 page 级 I/O，又能用 direct backend 按 page-layer 执行标准 memcpy。

这里的 direct 仅指 CPU↔GPU 的 memcpy 路径，不表示 L3 绕过 L2 直达 GPU。

page_first_direct 也不是无条件更快：它优化的是每个 copy 的连续性，不是把整个 prefix 变成一次大 copy。对于跨 N 个 pages、包含 L 层的 MHA KV，完整搬运仍对应约 2NL 个连续的 page-layer 区域（K、V 各一份）；批量 memcpy 可以合并提交，但无法消除地址计算、copy descriptor 构造和大量小块传输的调度成本。当 page 较小、层数较多或 prefix 跨越很多 pages 时，这些固定开销会更明显。

2.8 Prefill 之后：新 KV 如何回写？

GPU 只对未命中的 suffix 执行 Prefill 并生成新 KV，随后 Cache controller 按策略执行 L1→L2→L3：

策略 行为 主要取舍
write_through 新 KV 尽快备份到下一层并发布到 L3 覆盖率高，但写带宽开销最大
write_through_selective 达到访问热度阈值后再写 L3 过滤一次性 prefix
write_back KV 先留在快层，驱逐时再向下写 减少常态 I/O，但驱逐路径更复杂

L2 写 L3 前会查询 page 是否已经存在，只传输缺失数据。

2.9 用一个 12K Prompt 串起完整流程

假设缓存分布为：

  1. Local Match 得到 4K L1 hit + 3K L2 hit，本地连续命中 7K；
  2. 查询剩余 5K，发现 L3 中接下来的 4K 连续存在，最后 1K miss；
  3. TP ranks 对 L3 命中长度执行 all_reduce(min)。本例假设所有 ranks 都命中 4K，因此全局结果仍为 4K；如果四个 ranks 报告 4K/4K/3K/4K，全局结果就只能是 3K。最终长度超过预取阈值后，各 ranks 按同一个长度发起 L3→L2；
  4. wait_complete 下，4K 全部到达后复用前 11K，只 Prefill 1K；
  5. timeout 下，若只有前 2K 按时到达，则最终复用 9K，剩余 3K 重新 Prefill；
  6. L2 中的 prefix 按 layer 加载到 L1，并与 suffix Prefill 重叠；
  7. 新生成的 suffix KV 按回写策略进入 L2/L3，供后续请求复用。

2.10 HiCache 与 PD 分离是什么关系？

两者解决不同问题：

  • PD transfer：把本次请求刚由 Prefill 节点算出的 KV 送到 Decode 节点；
  • HiCache：跨请求、跨时间保存历史 Prefix KV，减少未来请求的 Prefill。

启用 Decode 侧 KV offload 后，数据传输：

flowchart LR
    P["Prefill"] -->|"本次请求：Prompt KV 直传"| D["Decode"]
    D -.->|"Decode KV 回写"| L3[("L3 Storage")]
    L3 -->|"后续请求：Prefix KV 读取"| P
    P -.->|"Prompt KV 完整页回写"| L3
  • P → L3 负责 Prompt KV：Prefill 按 HiCache 写策略回写 page-aligned 的 Prompt KV，包括本轮新计算的 suffix 完整页。
  • D → L3 只补增量 KV：开启 --disaggregation-decode-enable-offload-kvcache 后，Decode KV 回写，覆盖 Prompt 不足一页的尾部和新生成的 Decode KV；未开启时，这条边不存在。

3. 命中不等于收益：什么时候加载，什么时候重算？

一次缓存加载包含元数据查询、I/O 排队、固定启动成本、数据传输、布局转换和多 rank 同步；重算成本则是对应 prefix 的 Prefill 时间。只有加载暴露在关键路径上的时间低于被省掉的 Prefill 时间，这次复用才真正有收益。

  • 小 prefix 即使命中也可能应直接重算；
  • 长 prefix 即使位于远端，也可能明显比重算便宜；
  • 同一 prefix 在低负载时可能适合重算，在 Prefill 队列拥塞时更适合读取；
  • best_effort、timeout 和 wait_complete 本质上是在 TTFT SLO 下选择不同的 I/O 风险敞口。

prefetch_threshold 应由实际模型的 Prefill 曲线、KV bytes、L3 尾延迟和有效传输带宽共同校准。生产判断应看 saved_prefill_time - exposed_load_time，而不是把 cache hit rate 当作最终目标。
